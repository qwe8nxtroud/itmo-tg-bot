# Правила работы с проектом

Telegram-бот «AI-ассистент студента» (курс «Технологии ИИ в разработке ПО», ЛР № 1–3).
Python 3.12, aiogram 3, asyncpg + PostgreSQL, MCP Python SDK 2.x.

## Каталоги

| Путь | Назначение |
|---|---|
| `app/` | Telegram-приложение (MCP-хост): конфигурация, LLM-клиент, сервисы, хранилище |
| `app/handlers/` | Обработчики Telegram. Только разбор update и отправка ответа, без бизнес-логики и SQL |
| `app/migrations/` | SQL-миграции, применяются по порядку номера при старте бота |
| `mcp_server/` | MCP-сервер: инструменты `get_weather`, `get_schedule`, `add_reminder`, ресурс `schedule://current-week` |
| `data/schedule.json` | Обезличенное учебное расписание (без персональных данных) |
| `scripts/` | Локальный запуск, деплой, независимая проверка MCP, эксперименты |
| `tests/` | Автотесты: офлайн по умолчанию, `-m integration` — на PostgreSQL |
| `docs/` | Методичка, спецификация, план, эксперименты, отчёты |

## Команды

```bash
uv venv -p 3.12 .venv && uv pip install -p .venv/bin/python -r requirements-dev.txt
.venv/bin/python -m pytest -q                      # офлайн-тесты
RUN_INTEGRATION=1 .venv/bin/python -m pytest -m integration -v   # нужен PostgreSQL
.venv/bin/python -m ruff check . && .venv/bin/python -m ruff format --check .
.venv/bin/python -m pip check                      # или uv pip check -p .venv/bin/python
.venv/bin/python -m scripts.mcp_check              # независимый MCP-клиент
.venv/bin/python -m scripts.eval_routing           # оценка маршрутизации (нужен LLM)
bash scripts/deploy_server.sh vh-tw                # деплой на сервер с Docker по SSH
```

## Архитектурные границы

- **Обработчики** (`app/handlers/`) вызывают сервисы `Assistant` и `Agent` и не знают о SQL,
  MCP и схемах инструментов.
- **Сервисы** (`app/assistant.py`, `app/agent.py`) собирают контекст, вызывают модель и
  проверяют решения. Агент получает схемы только из MCP-обнаружения.
- **Хранилище** (`app/storage.py`) — все SQL-запросы приложения, только параметризованные
  (`$1`, `$2`). Сервер MCP пишет только в таблицу `reminders`.
- **MCP-клиент** (`app/mcp_client.py`) — единственное место работы с MCP-сессией. Ошибки
  он приводит к `ToolCallError(code, message)`.
- **MCP-сервер** (`mcp_server/`) не импортирует `app/`. Общий с приложением только модуль
  подписи доверенного контекста `mcp_server/trust.py`.
- Владелец, чат и ключ идемпотентности берутся из Telegram update, а не из ответа модели.

## Миграции и переменные окружения

- Новая таблица или колонка — это новый файл `app/migrations/NNN_*.sql`. Применённые
  миграции не редактируются. Данные не удаляются ради исправления ошибки схемы.
- Новая переменная: пример в `.env.example`, чтение и проверка в `app/config.py` с
  понятной ошибкой, проброс в `compose.yaml`. Если переменная нужна MCP-серверу —
  ещё и в `app/mcp_client.py::server_environment`.
- Зависимости только с закреплёнными версиями в `constraints.txt`. `pip check` должен
  проходить.

## Тесты

- Без реальных Telegram, LLM и погодного API: внешние границы подменяются фейками
  (`tests/fakes.py`) и фикстурами. Текущее время всегда подменяемое.
- Для каждого поведения нужны успешный и хотя бы один ошибочный или пограничный сценарий
  в порядке Arrange — Act — Assert. Проверяются точные значимые поля.
- Механизмы защиты от дублей проверяются интеграционно на PostgreSQL.

## Секреты и персональные данные

- Нельзя коммитить `.env`, `.env.*` (кроме `.env.example`), токены, ключи, пароли, дампы
  и журналы с данными пользователей.
- В текстовый лог не пишутся Telegram ID, имена пользователей, тексты сообщений,
  системные промпты и ключи. Для корреляции используется `request_id`.
- Расписание в репозитории только обезличенное. Реальное расписание подключается через
  `SCHEDULE_PATH` вне Git.
- Секрет, попавший в Git, считается раскрытым и перевыпускается.
